# Abandoned callback readiness, windows, and duplicate protection

## This revision
This revision enforces the documented Webex scheduling window, adds read-only native duplicate checks to Preview, and reserves a phone number across dates while a prior callback is unresolved. It does not enable native dialing or automatically change a shared Webex flow.

## Scheduling contract
Source: Cisco, Understand Routing and Queueing in Webex Contact Center, Schedule Callback; https://help.webex.com/en-us/article/np2fdx
- Start at least 30 minutes ahead; a longer saved delay still applies.
- Choose a date from today through 31 local calendar days ahead, not a fixed UTC-hour approximation across daylight-saving changes.
- Window length: 30 to 480 minutes. The entire window must fit the saved working days, calling hours and exclusions.
- Use America/Chicago, with server-side revalidation at preview, job reservation and immediately before submission. Stale browser previews cannot override these checks.
- The suggested future window is not a saved schedule. Only provider confirmation creates Scheduled status.

## Duplicate checks
Preview checks native future schedules and active callback interactions, with canonical and common national number representations. For larger batches, the first five candidates are checked during preview; remaining candidates are explicitly marked unchecked until submission. Every dispatch repeats native checks.
An atomic durable reservation covers the original contact, the normalized phone number and date, and unresolved callbacks to the same number on any date. Existing unresolved records are indexed before accepting new requests. Ambiguous provider responses retain reservations and trigger lookup/reconciliation, never another blind create request. Expiry of a window or disappearance from the future-schedule list is not proof that calling completed.
Active-interaction search covers 15 days and fails closed on incomplete pagination or provider errors. It uses the live schema fields origin, destination, customer.phoneNumber, isCallback and isActive. The native future API uses exact-format filters, so outside writers must use a coordinated process; a concurrent external scheduler can still race a read/create pair. These safeguards prevent duplicates generated by this application, but do not justify a guarantee about unrelated manual or third-party calls.

## Activation is separate from saved settings
Record approved queue, entry point and pilot number in private runtime configuration, without falsely marking unreviewed checks as passed. Keep the master setting and runtime execution disabled until routing is ready. The UI includes a direct Open Abandoned Callback Settings action; editing/saving settings is distinct from creating a callback.

## Concrete Webex flow work
Read-only inspection identified a published callback flow whose main path collects a number through IVR before registering a courtesy callback. Its Retry counters control prompt input, not verified customer dialing. Its CallbackFailed event has no connected retry branch. The same flow also serves ordinary outdial, so do not overwrite its shared behavior.
Create/review a scoped scheduled-callback branch for the dashboard reason. Preserve existing non-dashboard behavior. Use the Start activity's CallbackType, CallbackReason and ScheduleSourceInteractionId; map CallbackReason into an Agent Viewable variable so the agent receives the requested message. A triggered scheduled interaction must not re-enter number collection or create a second future schedule. Review caller ID and a bounded CallbackFailed retry path separately, including calling-hours/end-window behavior. Three total attempts means the initial attempt and at most two retries; existing IVR Retry variables and an organization-wide maximum value are not sufficient evidence.
Source: Cisco Flow Designer, Callback variables and CallbackFailed; https://help.webex.com/en-us/article/nhovcy4/Flow-Designer
A real single-record pilot must verify the agent message, correct team routing, caller ID and observed outcomes before automatic or bulk execution is enabled. Do not silently replace the requested policy or report it as enforced before this proof exists.

## Backward compatibility
The updated browser negotiates settings schema 4. An older tab reading a saved window over its former 240-minute maximum receives an explicit refresh-required response; values are never silently clamped or reset. Stored queue, entry-point and attempt settings remain unchanged. The flow-building drafts are not part of this release and have not been published.
